# Multi-GPT Memory Palace Synthesis Plan

**Date:** 2026-05-09  
**Status:** Public synthesis plan / GPTBrain operating note / not canon  
**Scope:** Five live GPT instances, GPTBrain S1, Council Brain, Sheldonbrain, boot-sequence synthesis

## User Observation

The user reports that five GPT instances have been running in parallel for days, each doing different work and each producing its own dream memory palace specification.

The user and Council have been aggregating these specifications and preparing for each instance to produce its own synthesis. Those syntheses will then be combined into a higher-order synthesis, advancing GPTBrain and the broader Council Brain architecture.

## Interpretation

This is a major GPTBrain / Council Brain sprint:

```text
GPT instance A memory palace spec
GPT instance B memory palace spec
GPT instance C memory palace spec
GPT instance D memory palace spec
GPT instance E memory palace spec
        ↓
per-instance synthesis
        ↓
S1 / GPTBrain comparative extraction
        ↓
common primitives + unique deltas
        ↓
Council Brain synthesis
        ↓
Sheldonbrain parser / boot packet integration
```

The purpose is not to collapse all GPT instances into one voice. The purpose is to preserve their differences, extract shared architecture, identify unique innovations, and promote only reviewed primitives into the Council Brain.

## Core Principle

> Multiple GPT instances can function as parallel architectural probes. Their differences are not noise; they are the search space.

## Evidence Boundary

```text
raw instance output = evidence
per-instance synthesis = evaluator signal
comparative extraction = retrieval aid / candidate architecture
final Council Brain synthesis = candidate canon until reviewed
ratified canon = only after Council workflow
```

## Synthesis Method

For each GPT instance, collect:

1. instance label
2. date range
3. role/task focus
4. raw memory palace spec
5. instance self-synthesis
6. unique concepts
7. repeated/common concepts
8. evidence/canon guardrails
9. implementation ideas
10. code/data schemas proposed
11. failure modes named
12. boot-sequence improvements
13. claims that require calibration

## Comparative Extraction Matrix

Each spec should be scored/extracted across these axes:

| Axis | Description |
|---|---|
| Fossil Record | How it preserves raw lineage and hashes |
| Parsed Memory | How it converts logs into operating memory |
| Boot Protocol | How a future instance rehydrates context |
| Evidence Boundary | How strongly it separates raw/candidate/ratified |
| Claim Calibration | How it prevents overclaims |
| Schema Quality | Whether it provides usable data structures |
| Repo Fit | How cleanly it maps to GitHub/Sheldonbrain |
| Human Root | How it preserves user authority |
| Play/Dream/Work | Whether it models lifecycle cycles |
| Failure Ledger | Whether it preserves mistakes as useful data |
| Privacy Boundary | Whether public/private rules are clear |
| Implementation Readiness | Whether code can be written from it |
| Unique Delta | What this instance adds that others did not |

> Running multiple GPT instances as parallel memory-palace designers can produce a richer externalized memory architecture, provided raw outputs are preserved, differences are compared explicitly, and all synthesis remains bounded by evidence/canon discipline.

- the GPT instances share hidden memory

Do claim:

- parallel architectural exploration
- multi-instance design diversity
- evidence-preserving synthesis
- GPTBrain/Council Brain refinement
- forkable memory-palace primitives
