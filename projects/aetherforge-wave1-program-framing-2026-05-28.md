## #3 v2 completion criteria

1. All 144 tasks have execution artifacts or explicit disposition.
2. Every completed task links evidence from board → artifact → validation surface.
3. Candidate/canon boundary remains explicit in all artifacts.
4. Wave-level outputs are linked from index surfaces (`README.md`, `projects/README.md`).
5. No critical path gaps remain in governance, provenance, or CI domains.

## #4 v2 governance checkpoints

1. Governance state machine references are present in all new promotion-related artifacts.
2. Canon-candidate register and related receipts are updated for each promotion decision.
3. Ratification path includes event identifier, adjudicator, and trust state.
4. Governance workflow changes include changelog notes and review metadata.

## #5 v2 trust checkpoints

1. Provenance fields are complete for all new execution artifacts.
2. Source and evidence links are present and machine-traversable.
3. Trust-state transitions are explicit and auditable.
4. Contradiction or uncertainty states are marked rather than silently normalized.

## #6 v2 quality checkpoints

1. Internal links resolve for touched artifacts.
2. Required metadata fields are present.
3. Task outputs are indexed and discoverable from board surfaces.
4. Validation results are captured for touched surfaces.

## #7 v2 release checkpoints

1. Wave completion receipts exist before release planning artifacts.
2. CI path/check matrix is updated before release candidate declaration.
3. Release readiness includes integrity checks and rollback references.
4. Public-facing release docs link back to governance and provenance evidence.

- Reviewer throughput and unresolved-review aging.

### Archive-growth KPIs

- Net new indexed artifacts per wave.
- Artifact metadata completeness percentage.
- Provenance-complete artifact percentage.
- Cross-link density growth (related links per artifact cohort).

## #12 Hypercube v2 execution charter

### Mission

Deliver a world-class, public, open-source execution program for the Next-144 backlog with explicit governance, provenance, and quality controls.

### Operating principles

1. GitHub remains the durable canonical substrate.
2. Candidate/canon boundaries are always explicit.
3. Every task ships with evidence and linkable receipts.
4. Quality and trust gates are part of normal flow, not optional overlays.
5. Execution remains publicly legible through indexed artifacts.

### Sequence discipline

- Work proceeds in strict wave order (1→12) unless a blocker requires documented exception handling.
- Cross-wave dependencies are captured before exception work begins.

### Accountability model

- Suggested owner lanes by wave are defaults unless explicitly reassigned.
- Each completed task must cite owner lane, acceptance evidence, and validation result.

### Exit conditions for Wave 1

- Master board confirmed as source of truth.
- v1→v2 dependency map published.
- Completion criteria, checkpoints, KPIs, risk template, and charter published.
